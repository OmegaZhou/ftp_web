## 目标

把 FTP Web 迭代为顺畅、易理解的文件工作台，提供文件夹上传、断点续传、持久化传输任务和明确的后台运行体验。保留现有 Nginx 100 MiB 请求体限制，采用分段上传解决大文件问题；块大小必须经过真实链路测试再决定。

## Proposal

以下保留 2026-10-23 方案阶段的初始 Proposal；实现、实测与发布结果以“当前进度”和后续证据为准。

- **意图**：形成可直接指导开发与验收的统一方案，用 UI 预览明确交互方向，用测试选择门约束块大小与并发配置。
- **问题背景**：此前排查发现整文件上传受代理限制、浏览与传输争用 FTP 连接、连接丢失时请求挂起、普通错误误退出、特殊文件名处理不安全，以及上传进度没有覆盖 FTP 转存。本地仓库与线上修复存在漂移，Android 客户端仍使用旧接口。

| 上传客户端 | `tus-js-client` + 自有任务面板 | 使用成熟 offset 恢复、重试与 URL 恢复逻辑；避免同时维护 Uppy 与自研两份任务状态。若目录选择/恢复适配成本高，可改用 Uppy Core + Tus 等必要模块，不加载全插件包。 |
| 后端 | Node.js + Express，新增模块使用 TypeScript | 复用现有服务和路由基础；先确认线上运行时兼容，再锁定依赖版本。当前 tus-node 官方要求 Node >= 20.19，实际选用受支持的运行时并记录版本。 |
| HTTP 接收 | `@tus/server` + `@tus/file-store` | 顺序追加到同一暂存文件，避免独立块文件合并产生完整第二份复制。请求体必须直接交给 tus 流处理，不先经 JSON/multer/内存缓冲消费。 |
| 任务与事件 | SQLite + 进程内受控 worker | 保存任务、所有者、目录清单、状态、偏移快照、尝试次数、租约及事件序号。首版单机服务足够，不引入 Redis。SQLite 与暂存文件位于持久目录，部署不能清空。 |
| FTP | 独立浏览连接与专用传输连接 | worker 每次尝试使用专用连接或受限连接池；不与会话浏览命令混排，设置超时、关闭及重连策略。 |
| 状态同步 | 轮询为可靠基线，SSE 可选增强 | 轮询根据活跃状态调整频率；SSE 断线后先获取持久快照，按事件序号补齐，不依赖代理即时 flush。保留 Nginx 现有配置。 |

技术版本在实施锁定时重新核验。tus 的认证由应用负责；`@tus/file-store` 当前支持矩阵**没有 Checksum 和 Concatenation 扩展**，不能声称库已提供逐块校验或单文件并行合并。[tus 协议](https://tus.io/protocols/resumable-upload)、[tus-node 支持矩阵与运行时要求](https://github.com/tus/tus-node-server#extensions)

传输主路径：浏览器选择文件/目录 → 建立任务清单 → tus 顺序 PATCH 写入暂存文件 → 完成完整性确认 → 持久化入队 → 专用 FTP 连接写临时目标 → 校验可用信息并 rename → 标记成功并清理暂存。

### 身份、授权与恢复

`stableUserId` 由服务端根据经 FTP 验证的账号、服务器标识和允许根目录建立稳定映射，不使用 session ID 作为任务所有者。所有任务、upload URL、事件和操作均校验 ownership；客户端 metadata 中的 userId/path 只是输入，不能授予权限。

上传路由只依赖有效用户身份与任务授权，**不能复用“session 对应 FTP client_map 中存在连接”的旧鉴权条件**。FTP 浏览连接断开不影响已收到数据和任务记录；失效连接单独重建。新接口统一返回可区分的 401、403、409、413、507 和结构化错误，所有分支都结束响应。

30 分钟登录过期后暂停后续 PATCH、提示重新登录并保留队列；重新认证同一 stableUserId 后读取任务和 HEAD offset，再继续。IndexedDB 保存任务元数据、upload URL 与本地文件候选指纹，不保存明文密码；文件名/大小/修改时间与抽样指纹仅用于定位候选，最终完整哈希负责防止选错文件。无法重新取得 File 对象时要求重选原文件/目录，明确展示需要重新关联的条目。

HTTP cookie 使用同源、安全属性与 CSRF/Origin 校验；任务 ID 随机不可猜测不能替代授权。登录成功后只把 FTP 凭据放入受控内存凭据上下文，与浏览 session 的生命周期区分。页面关闭后，同一服务进程中已校验并入队的转存继续；用户显式退出则撤销凭据授权并让相关任务进入待授权状态。服务重启后任务仍在，但没有内存凭据的任务进入 `AUTH_REQUIRED`，再次登录后恢复。跨重启无人值守凭据托管不属于首版承诺。

### 上传完整性与持久化

单文件始终顺序 PATCH，以服务端确认的 offset 为准；超时、重复请求或 409 先 HEAD 对齐，再续传。跨文件并发作为独立参数控制；开发初始限制可以用于运行测试，但不能以此冒充性能选型结论。tus-js-client 的 `chunkSize` 对应单次 PATCH body 上限，必须显式设置为最终测试选值，不能沿用 Infinity。[客户端参数说明](https://github.com/tus/tus-js-client/blob/main/docs/api.md#chunksize)

客户端在 Web Worker 中流式计算完整 SHA-256，可与上传并行，禁止主线程先读入整文件或整文件 prehash 后才开始上传。断点恢复时可在 Worker 重新流式计算，内存保持有界；服务端在接收完成后流式计算独立摘要并与客户端声明值比较。这个完成确认是应用层设计，不是 tus Checksum 扩展。只有长度和摘要通过才进入 FTP 队列；摘要未提交时保持 `VERIFY_PENDING`，重开页面补齐确认。UI 在此期间显示“校验中/需要恢复校验”，不能宣告可以关闭页面。

接收长度、文件状态与 SQLite 元数据之间存在跨资源崩溃窗口，必须采用可重复执行的完成流程。`POST /complete` 只做 ownership、长度/状态等有界检查，在 SQLite 事务中持久化客户端摘要和 `VERIFYING` 意图，成功后立即返回 `202 Accepted` 及状态查询地址；不在 HTTP 请求中等待完整文件 hash 或 FTP。后台校验 worker 领取租约，确认实际长度/持久化检查点并流式验证摘要，通过后在 SQLite 事务内标记 READY 并创建唯一转存任务，再由转存 worker 领取。唯一键约束 `uploadId + destinationVersion`；重复完成调用返回已有状态，摘要与原声明冲突则报错，不能重复校验入队。不得仅在 `onUploadFinish` 内存回调中启动 FTP。

所有 HTTP 调用必须有明确的时间边界：控制类接口的执行预算低于现有 Nginx 超时，流式上传/下载设空闲超时、总生命周期与中止清理，SSE 按有界连接周期重连。耗时工作通过持久任务查询，不以提高 Nginx 超时掩盖请求内长 hash 或 FTP 阻塞。启动 reconciliation 同时恢复已持久化但尚未领取或中断的 `VERIFYING` 工作。

启动和周期 reconciliation 检查暂存文件、tus 元数据、任务表与租约：恢复未处理的完整上传、清除过期租约、将缺少凭据的工作置为待授权、隔离缺失/长度不一致的数据并说明错误。崩溃恢复的 offset 不能超过已持久化的字节；实现时验证所选 file-store 的落盘语义，必要时增加 fsync 检查点和偏移修复适配。普通断网和进程重启必须可恢复；机器断电的持久性边界单独验证，不能把库支持续传等同于事务持久性。

### FTP 转存与后台边界

每个文件先写入目标目录内随机、带任务标识的临时名称；上传完成后检查 FTP 可用的大小/摘要信息，最后 rename 为正式名称。只有正式目标确认后才标记成功。大小一致只能证明长度，不等于摘要一致；客户端→暂存文件的校验与客户端→FTP 目标的端到端校验必须分别记录，不能混用结论。不同 FTP 服务器对覆盖 rename、REST+STOR 和哈希命令支持不同，必须针对当前服务验证，不能仅凭 FEAT 输出宣布支持。

FTP 中断后保留服务器暂存文件，退避重试；若 REST 上传偏移实测可靠，可从已验证的远端偏移继续，否则从服务器暂存重新传输完整文件，**不要求浏览器重新上传**。在“FTP 已完成但数据库未更新”的崩溃窗口，reconciliation 先核实本任务临时/正式目标与大小/可用摘要；证据不足时保留源文件并进入人工可见的重试状态，不盲目覆盖同名文件。

临时名与正式目标位于同一目录；无覆盖的 rename 原子性、已有目标处理及大小写规则在能力测试中确认。整文件完成可作为提交边界，整个目录上传不提供事务回滚。

| 用户情景 | 产品承诺 |
|----------|----------|
| 当前页面切换目录/标签页 | 队列独立存在；浏览器若继续调度，客户端上传继续。 |
| 关闭页面，文件仍在本机或待客户端摘要 | 不能保证继续；服务器保留已收字节，重开并重新关联文件后恢复。 |
| 完整文件已通过校验并持久化入队 | 服务进程存活且凭据授权有效时，关闭页面仍继续 FTP 转存。 |
| Node 重启 | 恢复任务记录和暂存文件；需要重新登录授权 FTP，随后恢复任务。 |
| 浏览器重启 | 恢复任务元数据，未完整上传的文件可能需要重选；不承诺后台持续读本机文件。 |

Uppy Golden Retriever 可改善刷新后的文件重新关联，但 IndexedDB 配额与临时 Service Worker 引用均有边界，不能据此承诺关浏览器仍上传。[Golden Retriever 官方说明](https://uppy.io/docs/golden-retriever/)

### 文件夹、路径、冲突与资源边界

选择文件夹/拖拽目录后生成 manifest，包含目录条目、文件相对路径、大小、修改时间及目标根目录。支持空目录：能枚举目录结构的入口保留空目录；只返回 FileList 的回退入口若无法发现空目录，要在提交前明确提示。manifest 分页/分批提交，遍历和统计避免阻塞主线程。

服务端将路径解析为 FTP 根目录内的规范绝对路径，拒绝绝对输入、盘符、NUL、`.`/`..` 穿越及编码混淆；每个编码边界只解码一次。Windows 本地目录分隔符转为规范相对路径；保留合法 Unicode 和 `%` 等文件名，不做不可逆的字符“修正”。明确大小写和 Unicode 规范化造成的冲突，并检查符号链接/FTP chroot 边界。文本展示使用安全 DOM 文本，禁止拼接 inline onclick。

同名文件默认询问一次可作用于本批：跳过、保留两份、替换。替换需明确确认；保存决策与目标版本，完成前重查目标防止覆盖并发创建的新文件。目录先创建后处理子文件，每文件独立成功/失败；批次展示成功、失败、跳过与目录数量（包含全部层级，不能冒称空目录数），重试只处理失败项。

创建任务时预留逻辑配额，检查全局/每用户暂存上限、单文件/批次大小、文件数、路径深度与可用空间；超过限额明确返回原因。约 50 GB 的现有磁盘必须按实际可用容量规划，计入 Nginx 请求缓冲、应用暂存、FTP 目标是否同盘、数据库和日志，不能只按 chunkSize 估算磁盘需求。

建议初始运维门槛为保留 `max(5 GiB, 文件系统容量的 20%)`，实施前按实际容量校准；新任务需满足预留预算，活动任务受空间告警和背压保护。暂停/未完整接收任务的保留期限先按 7 天不活动设计，UI 显示具体到期时间；任务层按 `lastActivity` 实施清理，不直接沿用 file-store 按创建时间计算的 expiration。活动租约、正在写入/校验/转存、待转存及转存失败但仍可恢复的文件均跳过自动清理，后两者通过显式取消或另行保留策略处理，避免上传很久后刚入队就过期。清理先标记、再在锁内复核、只删除已确认属于任务的暂存对象；成功后的暂存清理可重试，清理失败不把成功传输改为失败。

### 浏览、下载与 API 轮廓

新目录接口采用 `GET list?path=绝对路径&cursor=...&limit=...&sort=...`，不使用全局 cwd 作为请求隐式状态。浏览、上传和多个页面的路径互不影响；响应携带规范 path 和快照/cursor 版本。FTP LIST 可能仍需完整扫描，API 分页不能虚称为 FTP 端分页；使用有上限缓存、失效刷新和虚拟列表缓解，大目录性能另行实测。

下载使用 FTP 专用连接流式回传，客户端断开时关闭 FTP 流；明确 Content-Disposition UTF-8 文件名、Content-Length/类型和错误响应。HTTP Range 作为计划功能：先验证当前 FTP REST+RETR，支持才实现单区间 206/416、长度及偏移；不支持时返回完整 200 并不宣称支持 Range。不得吞掉流错误或再次 decodeURIComponent 破坏 `%` 文件名。

| API（建议轮廓） | 责任 |
|----------------|------|
| `POST /ftp/api/v2/batches`、分页 manifest 接口 | 创建用户所属批次、路径与冲突预检、预算预留；支持幂等键。 |
| `POST/HEAD/PATCH/DELETE /ftp/api/v2/uploads[/id]` | tus 创建、偏移确认、顺序追加与终止；每次执行身份和 ownership 校验。 |
| `POST /ftp/api/v2/uploads/:id/complete` | 持久化客户端摘要与 `VERIFYING` 意图后立即返回 202/查询地址；后台校验后幂等入队，不同步等待 hash 或 FTP。 |
| `GET /ftp/api/v2/tasks`、`GET /tasks/:id` | 分页获取任务/快照，返回两阶段字节、错误原因、可执行动作与到期时间。 |
| `POST /tasks/:id/{pause,resume,retry,cancel}` | 校验状态转换并持久化命令；暂停确认包含当前阶段和安全停止边界。 |
| `GET /ftp/api/v2/events?after=序号` | 可选 SSE 或事件轮询；历史超出保留窗时要求重新拉快照。 |
| `GET /ftp/api/v2/list`、文件操作与下载接口 | 显式绝对路径，浏览连接隔离；非认证错误在原页面显示。 |

任务状态建议：`CREATED → RECEIVING → VERIFY_PENDING/VERIFYING → READY → TRANSFERRING → FINALIZING → SUCCEEDED`。可恢复分支为 `PAUSED`、`AUTH_REQUIRED`、`RETRY_WAIT`、`FAILED_RETRYABLE`；终止分支为 `CANCELED`、`EXPIRED`、`FAILED_FINAL`。持久化 `phase + state`，避免暂停后丢失所处阶段。

暂停客户端上传时停止当前请求并以 HEAD 确认已收字节；暂停 FTP 转存时关闭当前流，保留本地暂存及远端临时目标，后续按已验证的 FTP 恢复能力处理。取消进入服务端确认流程，不能仅从 UI 隐藏；已成功文件不得因取消批次而删除。401 要求重新登录，网络/FTP/权限错误分别提示，不把普通错误变成登出。

## UI 与交互规格

视觉方向为“海边学院云端资料室”：整页可见插画场景，顶部轻导航，桌面左侧约 35% 为 GPT 龙娘大立绘与对话，右侧约 65% 为文件工作面板。采用湖蓝与淡紫、日系斜角标签及明净内容区，角色从侧栏小卡升级为页面主视觉，不显示“GPT 龙娘 / YOUR ARCHIVE COMPANION”名牌；原案署名只保留在页脚。文件列表、传输任务、菜单和弹层使用有对比度的独立底色，场景不铺在文件文字后面。深浅主题跟随宿主外观，场景选择独立于主题。统一字体、间距、圆角、图标和按钮高度，主要动作突出，状态色有限使用；块大小、协议、worker 等实现细节留在诊断页，不出现在日常传输流程。

默认展示晴昼场景、招手值日服龙娘与 Q 版宠物；“装扮与场景”弹层提供三张场景缩略卡、三张立绘缩略卡与宠物开关，选择立即生效。常驻“专注模式/陪伴模式”切换收起主立绘和对话、释放桌面横向空间，Q 版宠物由独立开关控制；默认停靠在页脚专用留白，可在预览根区域内自由拖动并留在放手位置。透明浮层穿透，仅宠物本体和打开的动作菜单接收指针；提示气泡不拦截文件操作，点击其他区域后收起。widgetState 版本升为 2，旧版陪伴关闭状态在首次升级时重置为开启，以呈现用户新确认的方向；此后保存用户本轮的模式、场景、立绘、宠物偏好与归一化位置。窄屏把角色舞台移到文件面板上方，保证 320 px 下仍能操作。角色只转述任务状态，原型明确标识演示，不虚构传输完成或后台能力。按用户追加的动态效果要求加入轻量 CSS 动效：主立绘保持静态清晰，场景慢速轻推、6 个光点、Q 宠待机轻摇与六姿势动作，以及切图淡入和按钮反馈。装扮弹层提供“启用动态效果”开关并持久化；系统 prefers-reduced-motion 优先，页面隐藏时暂停动效，点击动作通过 animationend 解除，不轮询、不模拟上传进度，也不冒充 Live2D 或逐帧动画。Q 宠可选自主活动只使用一个可取消的 12–18 秒 timeout；拖动、手动动作、睡眠、静态偏好、系统减少动态、页面隐藏与模态打开优先，禁止自动行动抢占用户操作。

Q 宠交互：PointerEvents / pointer capture 支持鼠标与触摸，移动超过 5 px 才视为拖拽，拖后抑制误点击；放手轻回弹并保存当前位置，resize 时重新限界。方向键每次移动 12 px，动作菜单提供“摸摸头、打招呼、跳一下、散步、打盹/醒醒、回到角落、收起”；装扮弹层可重新显示，并可关闭自主活动。姿势来自一张 3×2 透明图集：idle / wave / walk、jump / sleep / drag，由 CSS 选择单格，配合轻量动作而非伪称骨骼动画。系统减少动态时允许手动换姿势与拖动，但不播放动画或自动走动；模态打开时宠物层 inert。中断散步保存当下落点，避免下一次布局重算跳回旧位置。

上传选择后先展示文件夹树、数量、总量、目标位置与冲突处理，再开始队列；大目录扫描显示进度并可取消。拖拽只在文件区展示放置提示，提供等价按钮操作。上传到服务器 100% 后必须继续显示“校验中/保存到 FTP”，只在最终成功时显示完成；不用虚构固定权重把两个阶段合为一条误导性的总进度。

暂停立即反馈“正在暂停”，得到确认后变为“已暂停”；断网自动保留任务并在可恢复时退避重试；重登用弹层返回原页面及原路径。刷新后先展示服务器任务快照，再提示哪些本地文件需重新关联。仅当文件已校验且持久化入队后显示“可以关闭页面，服务器会继续处理”，并在首次出现时解释重启需重新授权边界。

移动端在约 768 px 以下使用单列文件列表、压缩面包屑、底部操作区与全屏传输抽屉；次要列折叠到详情，不依赖横向滚动完成核心操作。图标有文字/aria 标签，键盘可操作选择、菜单与弹层，焦点可见，关闭弹层恢复焦点；状态同时使用文字与颜色。触控目标至少 44 px，正文对比度目标符合 WCAG AA，尊重 reduced-motion。

撤销仅用于尚未提交的本地队列移除等可撤回事务；真正删除 FTP 文件/目录、替换已有文件必须确认范围，明确不可由 toast 撤销。批量删除展示数量与目标路径，递归删除必须显示目录名称；任务取消和文件删除为不同动作。

## 块大小 benchmark 与选择门

**当前状态：实网粗筛、复测及 1 GiB 确认已完成，正式选择 4 MiB 并发布 `measured` 报告标记；8 MiB 未被设为默认。** 下文保留最初测试计划，实际执行矩阵以“本次实网测试执行约定”和阶段结果为准。未执行的原计划样本不计入完成记录；旧链路、localhost 或单次测速不能决定真实部署块大小。

### 测试条件与数据预算

1. 先实现与待发布一致的 tus/file-store/校验/SQLite/FTP 链路，可靠性检查通过；固定代码版本、依赖、Node、浏览器、HTTPS、HTTP 协议、Nginx 配置和硬件，记录客户端网络与 VPS/FTP 位置。
2. 请求必须从用户实际客户端网络经过现有域名及 Nginx 到 VPS；使用同栈的隔离测试账号/命名空间和唯一任务前缀，目标为专用测试目录，不使用私人文件、不改 Nginx。真实路径无法访问时记录阻塞，不用本机测试替代。
3. 粗筛使用 256 MiB 不可压缩随机文件，主基准为一份 1 GiB 随机文件，固定摘要并复用。另设不超过 256 MiB 的混合目录：许多 1–64 KiB 小文件、1–20 MiB 中等文件、长 Unicode 路径及空目录；记录准确数量/总量，用于交互和请求开销测试。超过 100 MiB 的样本必须真正发送正文，不能只验证声明长度。
4. 事前计算客户端和服务端临时峰值、FTP 目标是否同盘、Nginx 缓冲及保留空间；一次只保留必要测试对象。以约 50 GB 磁盘为约束，测试客户端临时数据上限暂定 2 GiB，服务端测试空间上限暂定 4 GiB（含同盘 FTP 目标、代理缓冲及日志余量），仍需满足磁盘预留线。空间不足先减样本数/串行复用，不堆积所有轮次副本。只清理本轮任务拥有的测试对象。
5. 块大小候选为 **4/8/16/32 MiB**；**64 MiB 仅条件探测**，全部低于现有 100 MiB 上限。MiB 统一为 1,048,576 字节，报告不混用 MB。每次仅修改块大小，单文件并发固定为 1、跨文件并发固定；并发选型在块大小选择之后单独做。

### 运行顺序

先用不超过 64 MiB 的非计分样本预热连接和链路，再对 8/16/32 MiB 各用 256 MiB 文件做一次筛选，顺序随机；这三次仅用于缩小候选，不构成选值结论。选两名候选，各用 1 GiB 文件做至少 3 次计分重复，每轮打乱顺序，保留每次数据而非只报告最好成绩。

若 8 MiB 更稳定/更快或移动端、弱网内存与重传压力明显，加入 4 MiB；若吞吐随 16→32 持续提高且 CPU、内存、重传及交互指标均有余量，再探测 64 MiB。新增候选通过筛选后同样至少 3 次计分。首版选择一个可配置的固定块大小，不强求未经验证的自适应算法。避免无条件穷举所有文件、块大小、并发与网络组合消耗大量带宽；发现波动超过候选差异时，应增加重复或跨时段复测，不能宣布胜者。

基础流程客户端上行预算为 `64 MiB 预热 + 3 × 256 MiB 粗筛 + 2 × 3 × 1 GiB 正式测量 + 2 × 256 MiB 目录 = 7.3125 GiB`，同量数据还经过 VPS→FTP。按每轮完成后从 FTP 目标回读校验的保守预算，另增加 **7.3125 GiB FTP→VPS 下载流量**；三个传输方向合计 **21.9375 GiB（约 21.94 GiB）**，不含协议及重试开销，也不直接等同于云厂商计费流量。回读进程流式 hash 后丢弃字节，不额外落盘，也不再转发至客户端；若另测完整客户端下载，再单独增加 7.3125 GiB VPS→客户端流量，四段合计 29.25 GiB。若可信 FTP 摘要命令替代回读，记录实际省去的下载量，不预先假定可用。

每增加一个完整候选，粗筛加三轮正式测试分别增加 3.25 GiB 客户端上行、3.25 GiB VPS→FTP 转存和最多 3.25 GiB FTP 回读，合计 9.75 GiB；先核对余量再扩展。弱网、断线及故障注入使用 16–64 MiB 小样本，确需跨越多个块时扩大到所测块的至少两倍；不为每个故障重复 1 GiB 全矩阵。

### 选择规则与测试门

先过可靠性、内存/磁盘和 UI 硬门，再比较实际路径吞吐。建议验收目标如下，都是**待验证目标，不是已达到结果**：源文件与独立验证的 FTP 正式目标 SHA-256 一致率 100%，不能以暂存校验或大小相等替代；没有悬挂请求/任务丢失/跨用户读取；故障恢复不重传已确认的浏览器字节；无 OOM，服务 cgroup 峰值低于实测可用预算并保留至少 25% 余量；磁盘始终高于预留线；传输中目录 API p95 相对空闲基线恶化不超过 20%，且典型目录目标不超过 1 秒；常用 UI 操作 p95 目标低于 100 ms。

不能满足硬门的候选淘汰，不能用更快速度抵消正确性问题。对通过的候选比较重复测量的中位端到端耗时和上传阶段吞吐；速度差在约 10% 内且没有统计稳定差异时优先较小块，降低重传成本。10% 是本项目预先声明的决策阈值，不是行业常数；若 FTP 阶段成为共同瓶颈，应按浏览器上传阶段差异与资源成本解释，而不是夸大端到端收益。

实测结果须保留原始 CSV、采集工具/脚本版本、日期时区、代码提交、环境、样本摘要、预热/轮次标记、错误记录及选择理由。报告完成并审查通过后，才把选定块大小写入发布配置；若链路/代理/服务器显著改变，重新验证。任何临时开发数值都必须与正式默认配置分开。

### 故障注入与恢复测试

故障注入在本地/隔离环境进行；生产链路只运行有预算的非破坏吞吐测试。覆盖断网与浏览器刷新、重复完成调用、重复 PATCH、offset 409、接收/校验/入队/转存/rename 各阶段进程重启、30 分钟登录过期、FTP 断线、无权限、磁盘配额/ENOSPC、错误摘要、重选同名不同内容文件、并发同名目标、取消与清理竞态。

磁盘满使用隔离的小配额目录/模拟写失败；进程重启只重启测试服务，不干扰线上业务。逐项验证任务状态、可恢复 offset、暂存保留、用户提示、资源释放与重试幂等；没有真实能力验证前，FTP REST 上传和下载 Range 都维持“待验证”状态。

## 行业实践与引用

以下引用核验于 2026-10-23；外部能力可能变动，实施锁版本时重新核验。引用用于说明选型依据，不作为本项目性能结果。

- [tus 协议](https://tus.io/protocols/resumable-upload)：以 HEAD 获取偏移、PATCH 继续上传，认证另由应用实现；本项目采用该续传模型。
- [tus-node 支持矩阵](https://github.com/tus/tus-node-server#extensions)：当前 file-store 不提供 Checksum/Concatenation，促使本方案采用应用层完成校验和跨文件并发。
- [tus-js-client chunkSize](https://github.com/tus/tus-js-client/blob/main/docs/api.md#chunksize)：代理限制是显式设置块大小的合理场景；没有推荐所有项目统一使用 8 MiB。
- [Nextcloud 分块上传](https://docs.nextcloud.com/server/latest/developer_manual/client_apis/WebDAV/chunking.html)：分块之后还有最终组装/提交、配额和不活动过期机制；本项目借鉴生命周期管理，不照搬其独立块合并实现。
- [Amazon S3 分段限制](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html)：普通分段允许 5 MiB 到 5 GiB，末段例外；这是 S3 服务约束，不能推导本项目的最佳块大小，也不限制 tus file-store 测试 4 MiB。
- [Uppy Golden Retriever](https://uppy.io/docs/golden-retriever/)：浏览器恢复缓存有容量和生命周期限制，恢复本地文件能力必须降级为重新选择。
